# День 13 — Task State Machine

Отдельный проект на основе дня 12: Flask, CLI, DeepSeek, персонализация и три
слоя памяти сохранены. Состояние задачи переживает закрытие страницы и перезапуск.

Основной маршрут: **planning → execution → validation → done**.

## Запуск

Локальный API-ключ перенесён из проекта дня 12 в `.env`.

```powershell
cd D:\AIAdvent\advent-day-13-task-state-machine
python -m pip install -r requirements.txt
python -X utf8 web.py
```

Открыть **http://127.0.0.1:5013**. Остановка: Ctrl+C.
Повторный запуск той же командой восстанавливает доступ к задачам на диске.
В новом checkout скопируйте `.env.example` в `.env` и задайте `DEEPSEEK_API_KEY`.
Файл `.env` исключён из Git.

Детерминированный веб-сценарий без API:

```powershell
python -X utf8 web.py --offline
```

Режим явно помечен OFFLINE и использует только учебную задачу о вакансии.
Для произвольных целей запускайте без `--offline`.

CLI:

```powershell
python -X utf8 main.py
python -X utf8 main.py --offline
```

Без ключа доступны создание, просмотр, пауза и восстановление сохранённых задач.
Реальное планирование, выполнение и смысловая проверка требуют API-ключ.

## Команды

| Команда | Действие |
|---|---|
| `/new-task <цель>` | Создать и сразу сохранить задачу в planning |
| `/task-status <task_id>` | Этап, прогресс, текущий шаг, ожидание и ошибки |
| `/task-logs <task_id>` | Сохранённые логи запросов, ответов и использования профиля |
| `/continue-task <task_id>` | Выполнить одно очередное действие |
| `/continue-task <task_id> <ответ>` | Сохранить ответ и продолжить планирование |
| `/pause-task <task_id> [причина]` | Приостановить задачу |
| `/resume-task <task_id>` | Восстановить этап и выполнить одно очередное действие |
| `/list-tasks` | Показать сохранённые задачи |
| `/delete-task <task_id> --confirm` | Удалить выбранную задачу вместе с результатами и логами |
| `/clear-tasks --confirm` | Удалить все сохранённые задачи вместе с результатами и логами |

После вопроса в CLI можно написать обычный ответ, например Senior.
После перезапуска укажите ID: `/continue-task task-... Senior`.
В веб-панели есть поле ответа и кнопки действий. Команды также принимаются
в обычном веб-чате.

Продолжение выполняет одно действие: этапы и границы шагов видны.
Ожидание ответа сохраняет planning, без автоматической паузы.
Повтор продолжения при ожидающем вопросе показывает сохранённый вопрос без
нового вызова модели. Для done: «Задача уже завершена. Продолжение не требуется».

Старые команды дня 12, включая `/strategy`, `/memory`, `/task complete`,
`/analytics` и `/reset`, сохранены. `/task complete` очищает прежнюю working
memory; формальную задачу завершает только успешная валидация.
Очистка чата, `/reset` и закрытие веб-сессии не удаляют задачи.

## Удаление сохранённых задач

В панели задач доступны кнопки **«Удалить выбранную»** и **«Очистить все задачи»**.
Перед удалением браузер просит подтверждение. После очистки список и выбор
задачи обновляются. Удаляются JSON-файлы задач, включая результаты, ответы
пользователя, журнал переходов и логи запросов. Отменить удаление нельзя.
Профили, память и история чата сохраняются.

CLI и веб-чат принимают команды из таблицы с обязательным `--confirm`.
HTTP API: `DELETE /api/tasks/<task_id>` или `DELETE /api/tasks`,
тело запроса — `{"confirm": true}`. Ответ содержит `deleted_count` и
`deleted_task_ids`; без подтверждения возвращается 400, неизвестный ID — 404.

Пока задача выполняет запрос, удалить её нельзя, даже если уже нажата пауза:
нужно дождаться сохранения ответа. Очистка всего списка при наличии такого
запроса отклоняется целиком с кодом 409. Задачи без активного запроса можно
удалять на любом этапе, включая done, failed и paused.
После остановки и перезапуска процесса незавершённая старая операция
не препятствует удалению. Повторная очистка пустого списка возвращает 0.
При ошибке файловой системы сообщение показывает число уже удалённых задач.

## Профиль и логи при работе над задачей

В форме новой задачи выберите профиль: текущий пользователь, beginner,
developer или manager. Идентификатор сохраняется в `TaskState.profile_id`.
Продолжение использует профиль задачи, даже после перезапуска или смены
профиля обычного чата. Для задач старой версии профиль закрепляется при
первом новом запросе.

При каждом запросе загружаются актуальные настройки закреплённого профиля.
Язык, стиль, формат и подробность применяются к тексту внутри JSON-ответа;
служебная JSON-схема остаётся неизменной. Явные требования в цели задачи
имеют приоритет над настройками профиля. Служебные слова протокола вроде
«steps» больше не меняют пользовательский preferredFormat.

В панели задачи отображаются профиль, его настройки и переопределения
последнего запроса. Раздел «Логи запросов» показывает:

- этап и шаг, время начала и длительность;
- статус running, success, error или interrupted;
- модель, входные и выходные токены, оценку стоимости;
- профиль, факт загрузки из хранилища и включения в промпт;
- снимок применённых настроек и переопределений;
- полный запрос, ответ и ошибку.

Последние 100 записей сохраняются в `TaskState.request_logs` вместе с
задачей. Они доступны после перезапуска и очистки чата. В Task Context
логи не добавляются. В промпт не передаются история логов или API-ключ.
Во время работы панель обновляет состояние раз в 1,5 секунды.

CLI выводит краткую запись и настройки профиля после действия.
Полные записи доступны через `/task-logs <task_id>` и
`GET /api/tasks/<task_id>/logs`.

В offline-режиме логи явно показывают отсутствие API-вызова: демонстрационная
модель не применяет персонализацию и не расходует токены.

## Таблица переходов

| Состояние | Назначение | Допустимый следующий этап |
|---|---|---|
| planning | Уточнение цели, сбор данных, план | execution, paused, failed |
| execution | Выполнение текущего шага | validation, paused, failed |
| validation | Проверка результата и критериев | execution, done, paused, failed |
| paused | Пауза с сохранённым предыдущим этапом | Сохранённый этап либо failed |
| failed | Ошибка выполнения шага | execution, paused |
| done | Проверенный конечный результат | Нет |

`TaskStateMachine.transition()` проверяет таблицу и дополнительные условия,
обновляет updated_at и добавляет StateTransition. Состояние и журнал
записываются одним атомарным сохранением.
Переходы planning → done, execution → done и done → execution запрещены.
Для исполнения нужен план; перед обычным переходом в validation все шаги
должны быть completed. Возобновление возвращает только сохранённый этап.

Ошибка выполнения отмечает шаг failed и переводит задачу в failed.
Продолжение повторяет именно этот шаг.
Ошибки транспорта или формата ответа во время planning/validation сохраняются
в last_error, сохраняя этап для повтора без запрещённых переходов из failed.

## Архитектура

| Файл | Ответственность |
|---|---|
| `task_models.py` | TaskStage, StepStatus, TaskStep, ExpectedAction, PauseInfo, TaskQuestion, TaskState, StateTransition |
| `task_state_machine.py` | Таблица и проверка переходов, журнал |
| `task_repository.py` | TaskRepository, JsonTaskRepository, атомарное сохранение |
| `task_service.py` | Создание, вопросы, план, шаги, pause/resume, validation |
| `task_llm.py` | Типизированные результаты и проверка JSON-ответов модели |
| `task_context.py` | Task State в каждом связанном LLM-запросе |
| `task_commands.py` | Общие команды CLI и веб-чата |
| `task_demo.py` | Offline-модель и сценарий с отдельным процессом |
| `agent.py` | Существующий ChatAgent с дополнительным task_context |
| `main.py`, `web.py` | CLI, обычный чат и новый API /api/tasks |
| `templates/task_panel.html`, `static/tasks.js` | Панель задач |
| `tests/test_tasks.py` | Сервис, переходы, восстановление, гонки, атомарность |
| `tests/test_task_integration.py` | LLM-контракт, промпт и Flask API |

Модель предлагает вопрос, план или результат, но не изменяет этап напрямую.
Python проверяет ответ и применяет переход. Task-вызовы используют отдельный
краткоживущий ChatAgent с тем же клиентом и профилем. Истории задач не смешиваются.
Сравнение профилей и обычный диалог работают как прежде.

TaskState содержит поля задания: task_id, goal, stage, current_step_id, steps,
expected_action, pause_info, validation_issues, final_result, transition_history,
created_at, updated_at. Дополнительные поля:

- questions — идентификаторы вопросов, тексты и сохранённые ответы;
- acceptance_criteria — критерии готовности;
- last_error — последняя ошибка;
- operation_id — проверка принадлежности позднего ответа текущей операции;
- schema_version — версия JSON.

PauseInfo дополнительно хранит previous_action, восстанавливая конкретный
вопрос или действие. StepStatus: pending, in_progress, completed, failed.
ExpectedAction.actor: user, agent, tool.

## Хранение отдельно от чата

```text
data/
  tasks/task-<uuid>.json
  profiles/user_1.json
  memory/<conversation>.json
  demo-tasks/task-<uuid>.json
  demo-tasks/reports/task-<uuid>.json
```

TASK_DATA_DIR меняет каталог задач, по умолчанию data/tasks.
Сохранение выполняется после создания, вопроса, ответа, начала и завершения
шага, перехода, паузы и проверки. Сначала записывается уникальный временный
файл в том же каталоге, выполняется flush/fsync, затем os.replace.
Короткая блокировка файла индексатором Windows обрабатывается ограниченным повтором.
Неизвестный task_id и повреждённый JSON дают понятную ошибку.

История может сократиться, чат можно очистить, working memory дня 12 не
переживает перезапуск. TaskState независимо хранит цель, ответы и результаты.
В промпт передаются нужные поля, без всего JSON и журнала. Для валидации
передаются полные результаты. При превышении лимита контекста запрос
отклоняется с сохранением ошибки вместо проверки усечённого результата.

## Пауза и восстановление

Пауза доступна и во время запроса модели. Уже отправленный запрос не
отменяется у провайдера. Поздний ответ сохраняется, задача остаётся paused,
следующий шаг не запускается. После перезапуска completed-шаги пропускаются.
План, подготовленный во время паузы, используется без повторной генерации.
Сохранённый результат проверки также применяется без повторной проверки.

Граница гарантии: незавершённый LLM-вызов после аварии может повториться,
если ответ ещё не был сохранён. Проект генерирует текст и не выполняет
внешних действий. Для инструментов с побочными эффектами потребуется
идемпотентность на стороне инструмента. Actor=tool предусмотрен моделью,
но внешние инструменты здесь не подключены.

Проект рассчитан на один локальный процесс с несколькими HTTP-потоками.
Не запускайте CLI и сервер одновременно как независимые писатели одного
каталога. Для нескольких процессов потребуется межпроцессная блокировка или БД.
Список задач общий для локального приложения; демонстрационные профили
не являются учётными записями с авторизацией.

## Демонстрация для преподавателя

```powershell
python -X utf8 task_demo.py --offline
```

Сценарий выполняет запись JSON и запускает вторую фазу отдельным Python-процессом.
Модель детерминирована, ключ и сеть не нужны.

1. Создаётся задача о кратком описании вакансии Android-разработчика.
2. Сохраняется вопрос об уровне. Ответ: Senior.
3. Формируется план из трёх шагов и критерии готовности.
4. Первый шаг завершён; второй сохранён как in_progress.
5. Задача поставлена на паузу.
6. Новый процесс загружает JSON и продолжает со второго шага.
7. После второго и третьего шагов проверка обнаруживает отсутствие требований к опыту.
8. Только второй шаг возвращается в pending и исправляется.
9. Повторная проверка успешна: done.
10. Выводятся журнал переходов и итоговое состояние.

```text
planning → execution
execution → paused
paused → execution
execution → validation
validation → execution
execution → validation
validation → done
```

Отчёт в data/demo-tasks/reports/<task_id>.json содержит
`executed_after_restart = [2, 3, 2]` и `plan_calls_after_restart = 0`.

Вручную: запустите web.py --offline, создайте задачу, нажмите «Составить план»,
ответьте Senior, выполните первый шаг, нажмите «Пауза», остановите сервер,
запустите его снова с --offline, выберите задачу и нажмите «Возобновить».
Продолжайте до проверки, исправьте замечание очередным действием и повторите
проверку. Журнал и итог доступны в панели. Скрипт дополнительно фиксирует
начало второго шага перед паузой.

## Проверки

```powershell
python -B -m unittest discover -s tests -v
python -m compileall -q .
node --check static/tasks.js
```

Node нужен только для проверки JavaScript, не для запуска приложения.
Тесты не обращаются к реальному API. Проверяются основной маршрут,
запрещённые переходы, пауза в трёх этапах, повторная пауза, ошибки и повторы,
новый экземпляр и другой процесс, завершённая задача, неповторение шагов
и вопросов, атомарность и гонка с поздним ответом.
Интеграционные тесты проверяют JSON-контракт модели, Task State в каждом
запросе, Flask API и независимость задач от очистки чата.
